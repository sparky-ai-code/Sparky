Introducing Can: a virtual sandbox for AI agents

Agents that write code also need somewhere to run it. Can gives each agent its own small machine, with its own files, processes, ports and browser, kept apart from the computer it runs on.

By Sparky Lab · November 22, 2026 · Source on GitHub

Why agents need their own machine

Agents now do more than suggest code. They install packages, start servers, open pages in a browser and check their own work. On your own computer, that means trusting every line the agent writes and every command it decides to run.

Can gives the agent a place to do all of that. A can is a small virtual machine with its own filesystem, processes, virtual network ports, JavaScript runtime and headless browser. Code inside a can cannot read or write files on the host, start host processes, or see host environment variables.

What is inside a can

  • A filesystem with POSIX paths such as /app, /tmp and /home/agent.
  • Processes you can start in the background, list, read the logs of and signal.
  • Virtual ports, so a server running in a can can be reached from inside it.
  • A shell and a JavaScript runtime with the Node.js built-ins most projects use: fs, path, http, crypto, child_process and more.
  • A headless browser that opens local or internet URLs, reads pages, fills in forms, clicks, runs scripts and takes screenshots.

How the isolation works

Each can runs in its own child Node process, with Node's Permission Model turned on. That child can read only Can's own source folder. It cannot write files, start other processes, open workers or load native addons. It starts with an almost empty environment, the only exception being the variable Windows needs for name lookups, and its memory heap is capped at 512 MB. The host talks to it through a small asynchronous RPC client.

A second layer sits on top of the process boundary. It wraps every host value that enters can code, disables code generation from strings, removes escape hatches such as process.binding, and refuses to listen on host ports. The test suites include escape attempts, and they check that the process boundary holds even with this second layer switched off.

Can has no npm dependencies. It is built on Node.js built-ins only, which leaves very little third-party code to review before you run it. It requires Node.js 20 or newer. We run it on Node 24.15.0 and Windows 11.

Built to be driven by agents

Can runs as a Model Context Protocol (MCP) server over stdio. Sparky and any other MCP client that runs a stdio server can use it. Once it is registered, the agent has tools such as can_create, can_exec, can_write_file, can_spawn, can_ports, can_http and browser_goto.

A typical server session goes like this. The agent creates a can, writes server.js, starts it with can_spawn, finds the port with can_ports, and opens http://localhost:<port>/ in the can's browser. The browser returns a page snapshot with element references, so the agent can click and type by label or ref rather than guessing at selectors.

The same capabilities are available from a command line tool, for when you want to work with a can yourself:

node bin/can.js create demo
node bin/can.js exec demo -- echo "hello from the can"
node bin/can.js cat demo /app/a.txt
node bin/can.js ls
node bin/can.js rm demo

The full source is on GitHub at github.com/darkness22s/can, including the test suites mentioned above.

Moving files in and out

Files cross the boundary only through explicit calls. can_import copies a host file or folder into a can, and can_export copies a file back out. Both directions copy bytes, so PNG, gzip and other binary files arrive unchanged. Exports land only under a transfer folder on the host, and any path that tries to leave it is refused. Each call is limited to 256 MB per file, 500 MB in total and 5,000 files.

You can also mount folders read-only. You list the folders you are willing to share in one configuration file, and a can refers to them only by label. A mounted folder shows its current contents, and every write to it fails.

Set up a can before it starts

A can can be prepared from a spec before anything runs. The spec sets the start folder, copies in host files while leaving out folders such as node_modules and .git, writes files, sets environment variables and runs setup commands such as npm install. If a required step fails, the can is discarded and the error includes that step's output.

{
  "workdir": "/app",
  "node": "24",
  "imports": [{ "hostPath": "C:\\work\\my-app", "canPath": "/app", "exclude": ["node_modules", ".git"] }],
  "requireTools": ["npm"],
  "setup": [{ "command": "npm install", "label": "dependencies", "timeoutMs": 600000 }]
}

Packages install inside the can from the registry, so the host's binaries stay out. Packages that need install scripts or native addons are not supported yet. The project's README lists the full set of limits.

CI pipelines in a can

The same spec can drive a continuous integration pipeline. can_ci over MCP, or can ci pipeline.json on the command line, creates one fresh can and runs its jobs in order: a test job, a build job, and any others you define. A failing step stops the run, and a failed run keeps its can so you can inspect it. Artifacts are exported only when the whole pipeline passes.

Recording a session

A recording tool captures a QA session on a can. It writes a timeline of every call, with its arguments and result, and a video of the browser at each step that changes the page. The timeline has real timestamps. The video is a sequence of frames, one per step, meant for review.

Known limits

Can is strongest at JavaScript and shell work. These are the gaps today:

  • No native toolchains. There is no cargo and no C or C++ compiler. Install scripts and native addons do not run, and workspaces such as pnpm -r are not supported.
  • The default browser is a virtual DOM. Its screenshots approximate a layout so an agent can check it, but they are not pixel-accurate. Set chromiumBrowser to true in the configuration file to drive a real Chrome or Edge on the host instead. The can process stays sandboxed either way.
  • Outbound network is open. Node 24 has no --allow-net flag, so a can with internet access can connect out to any host. Listening on host ports is refused, but outbound connections are allowed by design.
  • CPU is not capped. Memory is limited to 512 MB, but a synchronous infinite loop will block that can until it is destroyed.
  • Tested on a narrow set of runtimes. The permission flags were verified on Node 24.15.0 only, although the package declares Node 20 or newer. Continuous integration runs the test suite on macOS with Node 20 and 24.

Try it

Can is a Sparky Lab project. It runs its tests with node --test, and there is nothing to install beyond Node.js. If your agents run code, give them a can rather than your own machine. Start with the commands above, then read the agent's timeline to see what it did.

The code is on GitHub at github.com/darkness22s/can. Clone it, run node --test, and open an issue if something breaks.
